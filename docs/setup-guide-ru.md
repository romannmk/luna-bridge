# Luna Bridge — полное руководство: установка, работа и публикация в open source

> Русская версия. Английская (каноническая) версия: [setup-guide.md](setup-guide.md).

> Маленький HTTP-мост между AI-агентом на телефоне и Muse Code на вашем Mac.
> Агент присылает задачу (и скриншот), мост запускает `muse` локально, агент забирает результат и отчитывается. Никакого SSH, никаких открытых портов в интернет.

## Что это и как устроено

Luna Bridge — это один файл `server.js` на чистом Node.js (только стандартная библиотека, ноль зависимостей, без сборки). Он крутится на Mac как launchd-агент и делает ровно три вещи:

1. Принимает файлы и задачи по HTTP с Bearer-авторизацией.
2. Запускает Muse Code CLI (`muse exec` — headless-задания, или интерактивный `muse` внутри tmux — shared-сессии) в указанной рабочей папке.
3. Отдаёт статус, вывод и экран сессии обратно агенту.

```text
Телефон (приложение Muse)
        │  задача + скриншот
        ▼
   AI-агент (Luna)
        │  curl, HTTPS/HTTP + Bearer token
        ▼
  Приватная сеть ──────────────┐
  (Tailscale / LAN / туннель)  │
        ▼                      │
  luna-bridge на Mac :8787 ────┘
        │
        ├── muse exec "<задача>"        → headless-задание (job)
        └── tmux: интерактивный muse    → shared-сессия (session)
        │
        ▼
  Результат → агент → отчёт на телефон (+ вопрос про draft PR)
```

Ключевой принцип архитектуры: **сеть — это отдельный, заменяемый слой.** Ядро моста не знает, как пакет попал на Mac. Ему нужен только IP, на который забиндиться, и HTTP-запрос с валидным токеном. Именно поэтому Tailscale можно убрать, не переписывая сервер (подробно — в разделе «Как убрать Tailscale»).

Текущее состояние проекта (5 ноября 2026): версия 0.1.0, работает в продакшене у автора каждый день. В репозитории на GitHub лежит начальный коммит; ещё 5 коммитов (фиксы install.sh и тестов, запрет печати токена, shared-сессии, model/effort) пока лежат локально на Mac и ждут пуша — это первый пункт чеклиста перед публикацией.

## Что нужно для работы

### Сторона Mac (где выполняется код)

| Компонент | Зачем | Как проверить |
|---|---|---|
| macOS, пользовательская сессия | Сервер работает от вашего пользователя, без sudo | — |
| Node.js 18+ (или Bun) | Рантайм сервера, зависимостей нет | `node --version` |
| Muse Code CLI, залогинен | Единственный бинарь, который запускает мост | `muse --version`, `muse exec --help` |
| tmux | Shared-сессии: интерактивный `muse`, к которому вы подключаетесь | `which tmux` (нет — `brew install tmux`) |
| git | Ветки, worktree, PR — это уже работа самого Muse Code | `git --version` |
| Приватная сеть до агента | См. раздел про Tailscale и альтернативы | `tailscale ip` |

Remote Login (SSH) **не нужен** — мост изначально проектировался как замена SSH.

### Сторона агента (кто присылает задачи)

- Любой клиент, умеющий делать HTTP-запросы с заголовком `Authorization: Bearer <token>` (в исходном сценарии — AI-агент Luna через `curl`).
- Клиент должен знать: базовый URL моста (`http://<ip-mac>:8787`), токен и рабочую папку проекта.
- Для сценария «с телефона» нужен только чат с агентом: пользователь пишет задачу и прикладывает скриншот, всё остальное делает агент.

### Доступы и подписки

- Подписка Muse Code у владельца Mac (задания тратят его квоту; параллельные сессии делят одну квоту на всех).
- Доступ к целевым репозиториям у Muse Code — как при обычной локальной работе.
- Аккаунт в выбранном сетевом сервисе, если это не LAN (Tailscale, Cloudflare и т.д.).

## Установка на Mac — шаг за шагом

### Шаг 1. Поставить зависимости

```sh
brew install node tmux   # если ещё не стоят
tailscale up             # или другой транспорт — см. ниже
```

### Шаг 2. Склонировать проект

```sh
git clone <url-репозитория> luna-bridge
cd luna-bridge
```

### Шаг 3. Создать конфиг

```sh
cp config.example.json config.json
```

`config.json` находится в `.gitignore` и никогда не уходит в репозиторий. Минимально нужно поправить:

- `default_workdir` — папка проекта по умолчанию, например `/Users/<you>/Projects/my-app`.
- `muse_bin` — полный путь к `muse`, если он не находится по PATH в окружении launchd (найти: `command -v muse`), например `/Users/<you>/.local/bin/muse`.
- `mode` — режим разрешений, по умолчанию `unrestricted`.
- Остальное на первый запуск оставить как есть (полный справочник ключей — ниже).

### Шаг 4. Первый запуск в foreground — получить токен

```sh
node server.js
```

Если токена ещё нет, сервер сгенерирует сильный токен (32 байта, hex), сохранит его в `~/.config/luna-bridge/token` с правами `0600` и покажет путь к файлу. **Само значение токена в stdout и в логи не печатается** (это был отдельный security-фикс: раньше значение попадало в лог launchd).

Проверка, что сервер жив:

```sh
curl http://127.0.0.1:8787/health
# {"ok":true,"version":"0.1.0","mode":"unrestricted"}
```

Остановить — Ctrl+C.

### Шаг 5. Передать токен агенту

Агент читает токен из файла `~/.config/luna-bridge/token` на Mac — когда у агента есть такой доступ — либо владелец передаёт значение один раз по защищённому каналу. Токен нельзя публиковать, коммитить и прикладывать к issue. Ротация токена: удалить файл и перезапустить мост — сгенерируется новый, старый перестанет работать.

### Шаг 6. Поставить launchd-агент (автозапуск при логине)

```sh
sh scripts/install.sh
```

Скрипт подставляет реальные пути и node в `launchd/com.luna.bridge.plist`, копирует его в `~/Library/LaunchAgents/com.luna.bridge.plist` и загружает. Логи: `logs/bridge.out.log` и `logs/bridge.err.log` в папке проекта.

Перезагрузка после обновления кода или конфига:

```sh
launchctl unload ~/Library/LaunchAgents/com.luna.bridge.plist && launchctl load ~/Library/LaunchAgents/com.luna.bridge.plist
```

Остановка: `sh scripts/uninstall.sh`.

### Шаг 7. Один раз проверить флаги Muse Code

```sh
muse exec --help
```

Мост опирается на флаги: `--yolo`, `--trust-workspace`, `--max-model-steps`, `--prompt-file`, `--workspace`, `--model`, `--reasoning-effort`. Если ваша версия CLI какой-то флаг не принимает — отключается конфигом (`prompt_via_file: false`, `use_workspace_flag: false`) без правок кода.

### Шаг 8. Проверить доступность снаружи

С устройства агента (или любого устройства в той же приватной сети):

```sh
curl http://<ip-mac>:8787/health
```

В логе старта должно быть две строки прослушивания: `127.0.0.1:8787` и `<приватный-ip>:8787`. Если второй нет — сеть не подхватилась: проверьте транспорт или задайте `bind_host` явно.

## Работа — шаг за шагом

### Обычное задание (headless job)

1. Пользователь пишет агенту задачу с телефона и прикладывает скриншот.
2. Агент загружает вложение: `POST /upload` (тело — файл, имя — в заголовке `X-Filename`). Файл падает в `data/inbox/` на Mac, мост возвращает путь.
3. Агент стартует задание: `POST /jobs` с `{prompt, workdir, attachments, model?, effort?}`. В промпте — пути вложений. Мост спавнит `muse exec` в `workdir`.
4. Агент поллит `GET /jobs/:id`, пока статус не станет `done` / `failed` / `cancelled`. Полный вывод пишется в `data/jobs/<id>/log.txt`, рядом лежат `prompt.txt` и `meta.json` — их можно смотреть прямо на Mac (`tail -f`).
5. Агент отчитывается пользователю и спрашивает про draft PR. **Ничего не мержится автоматически.**
6. Остановка по дороге: `POST /jobs/:id/cancel` (SIGTERM процессу и его группе, через `cancel_grace_ms` — SIGKILL).

### Shared-сессия (интерактивная, с подключением владельца)

1. Агент создаёт сессию: `POST /sessions` — мост запускает интерактивный `muse` внутри tmux-сессии `luna-<id>` с начальным промптом.
2. Владелец на Mac подключается в тот же живой процесс:

```sh
tmux attach -t luna-<id>
```

Отключиться без остановки сессии: `Ctrl+B`, затем `D`. Сессии переживают перезагрузку моста — tmux живёт отдельно.

3. Агент по просьбе владельца читает экран: `GET /sessions/:id/pane` — видит и запросы владельца, набранные прямо в сессии, и ответы агента. Действует правило «один водитель»: пока владелец печатает в сессии, агент в неё не пишет.
4. Агент может послать текст в сессию (`POST /sessions/:id/input`) — только по явной просьбе владельца.
5. Закрытие: `POST /sessions/:id/kill`.

Важно: живого attach к headless `muse exec` не существует в принципе — resume в Muse Code всегда поднимает новый процесс по event log, а работающая сессия заперта локом. Поэтому «подключаемая» работа делается только через tmux-сессии.

### Параллельные сессии в разных worktree

Параллельность заложена в дизайн: каждое задание — отдельный процесс со своей папкой. Worktree — обычная git-операция, её по просьбе агента делает сам Muse Code:

1. Подготовительное задание: `git worktree add ../<proj>-<branch> <branch>` для каждой ветки.
2. По одному заданию на worktree с разными `workdir` — они реально бегут одновременно (проверено живым демо: два полла подряд показывали оба задания в `running`, оба завершились с exit 0).
3. Уборка: удалить worktree и демо-ветки отдельным заданием.

Оговорки: квота Muse Code одна на всех; параллельные сборки могут спорить за общие кэши и порты dev-серверов; ветки расходятся и сливаются отдельными PR.

### Выбор модели и усилия на запуск

`POST /jobs` и `POST /sessions` принимают необязательные поля:

- `model` — свободный id модели, передаётся как `--model <ID>` (например, тяжёлая задача — на старшей модели, быстрая проверка — на лёгкой).
- `effort` — один из `none | minimal | low | medium | high | xhigh | max | ultra`, передаётся как `--reasoning-effort <TIER>`; по умолчанию `high`. Невалидное значение — `400`.

Дефолты задаются ключами `default_model` / `default_effort` в конфиге (по умолчанию `null` — флаг не передаётся, решает Muse Code). Эффективные значения пишутся в `meta.json` и возвращаются в статусах.

## Справочник API

База: `http://<ip-mac>:8787`. Все эндпоинты, кроме `GET /health`, требуют `Authorization: Bearer <token>`. Все ответы — JSON.

| Метод | Путь | Что делает |
|---|---|---|
| GET | `/health` | `{ok, version, mode}`, без авторизации |
| POST | `/upload` | Тело — файл, складывает в `data/inbox/`, возвращает `{path, name, size}` (201) |
| POST | `/jobs` | `{prompt, workdir?, attachments?, mode?, model?, effort?}` → `{job_id}` (202) |
| GET | `/jobs` | Последние задания, новые сверху |
| GET | `/jobs/:id` | Статус, `exit_code`, хвост вывода, `approval_blocked` |
| POST | `/jobs/:id/cancel` | Остановить задание |
| POST | `/sessions` | Создать shared-сессию в tmux, возвращает команду `tmux attach` |
| GET | `/sessions`, `/sessions/:id` | Список и статус сессий |
| GET | `/sessions/:id/pane` | Текущий экран сессии (capture-pane) + признак idle |
| POST | `/sessions/:id/input` | Послать текст в сессию |
| POST | `/sessions/:id/kill` | Закрыть сессию |
| GET | `/mode` | Текущий режим разрешений и его флаги |
| POST | `/mode` | Сменить режим для следующих запусков (сохраняется в конфиг) |

Статусы заданий: `queued | running | done | failed | cancelled`. Вывод в ответе — хвост до `max_output_tail_bytes` (200 КБ); полный лог — на диске в `data/jobs/<id>/log.txt`.

### Режимы разрешений

| Режим моста | Флаги `muse exec` | Смысл |
|---|---|---|
| `unrestricted` | `--yolo` | Без подтверждений и песочницы |
| `auto-review` | — | Автономная проверка рутинных действий (дефолт Muse Code) |
| `ask-me` | `--approval-mode on-request --approval-judge off` | Каждое подтверждение — пользователю; в headless-режиме задание встанет и мост отметит `approval_blocked: true` |
| `read-only` | `--disable-write --disable-shell` | Только чтение |

Плюс к каждому запуску: `--trust-workspace` и `--max-model-steps <cap>`, если кап задан.

### Ключи конфигурации

| Ключ | Дефолт | Смысл |
|---|---|---|
| `port` | `8787` | Порт HTTP |
| `bind_host` | `null` | Явный IP для бинда; `null` — автодетект (сейчас — Tailscale, см. ниже) |
| `data_dir` | `<папка сервера>/data` | `inbox/` и `jobs/` |
| `default_workdir` | `null` | Папка заданий без явного `workdir` |
| `default_model`, `default_effort` | `null` | Дефолтные модель и усилие |
| `token` | `null` | Токен; `null` — env `LUNA_BRIDGE_TOKEN`, иначе файл токена, иначе генерация |
| `token_file` | `~/.config/luna-bridge/token` | Где хранится сгенерированный токен (0600) |
| `muse_bin` | `muse` | Путь к бинарю Muse Code |
| `muse_args` | `[]` | Доп. аргументы к каждому `muse exec` |
| `mode` | `unrestricted` | Режим разрешений |
| `sync_muse_settings` | `false` | Писать ли режим ещё и в `~/.config/muse/settings.json` |
| `max_model_steps` | `300` | Кап шагов на задание (`0` — без капа) |
| `prompt_via_file` | `true` | Передавать промпт через `--prompt-file` |
| `use_workspace_flag` | `true` | Передавать `--workspace <workdir>` |
| `max_upload_bytes` | 25 МБ | Лимит загрузки |
| `max_prompt_bytes` | 200 КБ | Лимит промпта |
| `max_json_bytes` | 512 КБ | Лимит JSON-тела |
| `max_output_tail_bytes` | 200 КБ | Хвост вывода в памяти и ответах |
| `cancel_grace_ms` | `3000` | Пауза SIGTERM → SIGKILL при отмене |

Окружение: `LUNA_BRIDGE_CONFIG` — путь к конфигу, `LUNA_BRIDGE_TOKEN` — токен.

## Как убрать Tailscale

### Где Tailscale вообще «зашит» сейчас

Всего в двух местах, и оба — не в ядре:

1. **Автодетект адреса на Mac.** В `server.js` функция `detectTailscaleIp()` выполняет `tailscale ip --v4` и добавляет полученный `100.x.x.x` к списку биндов рядом с `127.0.0.1`. Если Tailscale не нашёлся и `bind_host` не задан — сервер слушает только localhost и честно предупреждает об этом в логе.
2. **Доставка запросов со стороны агента.** В исходной установке агент ходит на Mac через Tailscale-туннель своим `curl`. Причина историческая: из песочницы агента наружу разрешён только HTTPS через CONNECT-прокси, а сырой SSH через туннель не проходит (проверено экспериментально) — поэтому и родился HTTP-мост вместо SSH.

Всё остальное — авторизация, задания, сессии, tmux, worktree — от транспорта не зависит вообще.

### Что сделать, чтобы не тащить Tailscale

**Минимальный вариант (без правок логики, только конфиг):** задать адрес вручную.

```json
{ "bind_host": "192.168.1.50" }
```

**Правильный вариант для open source (небольшая доработка кода):**

1. Сделать `127.0.0.1` единственным безопасным дефолтом.
2. Заменить жёсткий `detectTailscaleIp()` на конфиг `bind_mode`: `localhost | tailscale | lan | custom` — где `tailscale` оставляет нынешний автодетект как опцию, `lan` биндится на LAN-интерфейс, `custom` берёт список из `bind_host`.
3. Вынести транспорт целиком в документацию: «мост слушает адрес X — как вы доставите туда трафик, ваше дело», с рецептами ниже.

### Варианты транспорта на замену

| Вариант | Как работает | Когда выбирать | Минусы |
|---|---|---|---|
| Та же LAN / Wi-Fi | Мост биндится на LAN-IP Mac (`192.168.x.x`) или имя `MacBook.local` (mDNS) | Агент и Mac в одной домашней сети | Не работает извне дома; Wi-Fi должен быть доверенным |
| SSH-туннель | Мост остаётся на `127.0.0.1`; клиент делает `ssh -L 8787:127.0.0.1:8787 user@mac` | Есть SSH-доступ; самый безопасный inbound | Нужен включённый Remote Login и SSH-клиент у агента; в исходной песочнице агента SSH был заблокирован |
| Cloudflare Tunnel | `cloudflared tunnel --url http://127.0.0.1:8787` даёт публичный HTTPS-адрес; именованный туннель — свой домен + Cloudflare Access поверх Bearer | Нужен доступ из интернета без VPN на клиенте | Зависимость от Cloudflare; публичный адрес обязательно прикрывать Access — одного Bearer по голому HTTP наружу недостаточно |
| Другой mesh VPN | ZeroTier, NetBird, WireGuard вручную, Headscale (свой control-сервер для Tailscale-клиентов) | Хочется тот же UX, но без Tailscale как сервиса | Это та же модель, просто другой провайдер; мосту всё равно — он просто биндится на IP интерфейса |
| Проброс без VPN | ngrok / bore / frp: `ngrok http 8787` | Быстрые демо и тесты | Публичный адрес, лимиты бесплатных тарифов, та же оговорка про HTTPS и доп. защиту |
| Relay / очередь (без inbound вообще) | Мост сам ходит наружу и поллит брокера (очередь, репозиторий, облако), забирает задачи и публикует результаты | Нельзя открыть ни одного входящего пути; максимальная «отвязка» от сети | Это уже переделка архитектуры, а не настройка; задержка поллинга |

### Рекомендация для публичной версии

- Дефолт — `localhost`, транспорты — документированные рецепты, Tailscale — первый рецепт в списке, но не требование.
- В README честно разделить: **ядро** (HTTP API, токен, задания, сессии) и **транспорт** (любой приватный путь между клиентом и Mac).
- Никогда не советовать бинд на `0.0.0.0` и публикацию порта в интернет напрямую: наружу — только через VPN, SSH-туннель или HTTPS-прокси с дополнительной авторизацией.

## Безопасность

- **Сеть:** бинд только на приватный интерфейс и `127.0.0.1`. Никогда `0.0.0.0` без файрвола и понимания, что вы делаете.
- **Авторизация:** Bearer-токен на всём, кроме `GET /health`; сравнение — constant-time (по SHA-256). Токен хранится в файле с правами `0600`, никогда не печатается в stdout и логи.
- **Исполнение:** сервер спавнит только бинарь `muse` (allowlist), напрямую через argv-массив, без shell — произвольные команды из запросов выполнить невозможно by design.
- **Валидация:** вложения принимаются только из `data/inbox/`; имена файлов санитизируются до basename (без path traversal); лимиты на размер загрузки, промпта и JSON; невалидный `model`/`effort`/`mode` — `400`.
- **Логи:** запросы логируются без промптов (только короткий preview в meta) и без токена. На диске каждого задания: `prompt.txt`, `log.txt`, `meta.json`.
- **Отзыв доступа:** остановить launchd-агент, сменить токен (удалить файл токена и перезапустить) или убрать устройство из приватной сети.
- **Режим по умолчанию — осознанный риск:** `unrestricted` (`--yolo`) означает, что присланная задача выполняется без подтверждений. Для публичной версии это должно быть громко написано в README, а не спрятано в конфиг.

## Структура проекта

```text
server.js                        сервер (Node stdlib only)
config.example.json              пример конфига
config.json                      ваш конфиг (gitignored)
launchd/com.luna.bridge.plist    шаблон launchd-агента
scripts/install.sh               установка и загрузка агента
scripts/uninstall.sh             выгрузка агента
test/fake-muse.sh                фикстура, притворяется muse CLI
test/run-tests.sh                end-to-end тесты (fake muse + curl)
data/inbox/                      загруженные вложения
data/jobs/<id>/                  prompt.txt, log.txt, meta.json каждого задания
logs/                            логи launchd
README.md, SETUP.md              документация
```

Тесты гоняются без настоящего Muse Code: `sh test/run-tests.sh`. В актуальной версии на Mac сьют проходит 99/99 (jobs, sessions, model/effort, auth, upload, cancel, валидация); в снапшоте v0.1.0 было 28 проверок.

## Известные ограничения

- Платформа запуска сервера — macOS (launchd, tmux, пути). Клиент-агент может быть где угодно. Порт на Linux (systemd) — естественное первое направление для контрибьюторов.
- Живого attach к headless-заданию не существует (ограничение Muse Code, а не моста); интерактив — только tmux-сессии.
- Завершение задания агент узнаёт поллингом; пуш-уведомлений о готовности, кроме отчёта агента, нет.
- Одна квота Muse Code на все параллельные задания и сессии владельца.
